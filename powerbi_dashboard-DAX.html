Level 0 — Foundations

Row Context vs Filter Context

Concept Meaning Typical Place Notes / When to Use
Row Context Evaluates one row at a time Calculated columns Use for per-row values: Year, flags, row-level categories.
Filter Context Evaluates over filtered set of rows Measures Use for totals/averages that react to slicers, axes, filters, cross-highlights.

Examples

Calculated Column

Year = YEAR(FactSales[OrderDate])

Output (per row): all rows show 2025 in this sample.

Measure

Total_Sales = SUM(FactSales[Sales])

Output (no filters): 650. By Category: Furniture=300, Tech=350.

Measures vs Columns (Quick Rules)

Question Calculated Column Measure Notes
Row-by-row transformation? ✅ ❌ Year, Month, flags, bucketing, keys.
Aggregation / totals? ❌ ✅ SUM, AVG, COUNT, ratios, KPIs.
Should react to slicers/axes? ❌ ✅ That’s what measures are for.
Used as axis / slicer field? ✅ ❌ Axis wants columns (fields). Measures go in “Values”.

Level 1 — Basic Aggregations (Measures)

Problem DAX (Measure) Example Use Sample Output Notes (When / Gotchas)
Total Sales 
Total_Sales = SUM(FactSales[Sales])
 Card / Bar chart by Category 650 (total) Respects filter context. With axis Category: Furniture=300, Tech=350.
Total Profit 
Total_Profit = SUM(FactSales[Profit])
 Card / Line chart over time 75 (total) Profit may be negative. Visuals can show negative bars/points.
Average Sales 
Avg_Sales = AVERAGE(FactSales[Sales])
 KPI 162.5 Average of rows in current context (not average per distinct OrderID unless 1 row per order).
Row count 
Row_Count = COUNTROWS(FactSales)
 Transactions count 4 Counts rows. If your grain is order-lines, it counts lines.
Distinct orders 
Distinct_Orders = DISTINCTCOUNT(FactSales[OrderID])
 Unique count 4 Use when there can be multiple rows per order.

Level 2 — Calculated Columns (Row-Level)

Problem DAX (Column) Example Use Sample Output Notes (When / Gotchas)
Year from date 
Year = YEAR(FactSales[OrderDate])
 Axis, slicer All rows: 2025 Best practice: do this in a proper Date table for time intelligence.
Fiscal Year (FY starts July) 
Fiscal_Year =
IF(
  MONTH(FactSales[OrderDate]) >= 7,
  YEAR(FactSales[OrderDate]) + 1,
  YEAR(FactSales[OrderDate])
)
 Fiscal reporting Jun rows FY=2025; Jul rows FY=2026 Great for FY slicing/grouping.
Profit flag 
Profit_Flag =
IF(FactSales[Profit] < 0, "Loss", "Profit")
 Legend / filter Row 2 = Loss Column is best for categories/flags used on axes/filters.

Level 3 — Data Types, Text, Formatting

Data Type Notes

Task Best Practice Why Gotcha
Currency / % formatting Format in Model (not via FORMAT()) Keeps numeric type (usable in math) FORMAT() returns text; breaks numeric sorting/math.

Text / Concatenation

Problem DAX Example Use Sample Output Notes
Concatenate (fast) 
Label =
FactSales[Category] & " #" & FORMAT(FactSales[OrderID], "0")
 Tooltip label Row 3: Tech #3 & is standard. Use FORMAT for ID rendering only.
Safe combine with delimiter 
Key =
COMBINEVALUES("-", FactSales[Category], FactSales[OrderID])
 Key, label, debugging Row 1: Furniture-1 More predictable with blanks than chaining & .
Uppercase 
Cat_Upper = UPPER(FactSales[Category])
 Normalization TECH Useful for comparisons / standard labels.

Formatting (Display vs Numeric)

Goal DAX Option Sample Output When to Use Warning
Percent label 
Margin_Text = FORMAT([Margin], "0.00%")
 "11.54%" Titles/tooltips only Returns text → don’t use in further calculations.

Level 4 — Logic, Blanks, Safe Math

Problem DAX Example Use Sample Output Notes
Safe divide 
Margin =
DIVIDE([Total_Profit], [Total_Sales])
 KPI 75/650 = 0.11538 Use DIVIDE to avoid divide-by-zero errors. Format as % in Model.
Blank instead of zero 
Sales_Blank_If_Zero =
IF([Total_Sales] = 0, BLANK(), [Total_Sales])
 Cleaner charts If 0 → blank BLANK often hides labels/marks; cleaner than 0.
Replace blank with 0 
Sales_0 = COALESCE([Total_Sales], 0)
 Tables where 0 is preferred 0 if blank Use for numeric display & total math consistency.
Multi-condition bucket 
Sales_Band =
SWITCH(
  TRUE(),
  FactSales[Sales] >= 300, "High",
  FactSales[Sales] >= 100, "Medium",
  "Low"
)
 Segmentation column 300=High, 200=Medium, 50=Low SWITCH(TRUE()) is a clean multi-condition pattern.

Level 5 — Selector (Sales vs Profit)

1) Disconnected Selector Table

Create a small table for a slicer (no relationships needed).

Metric Selector =
DATATABLE(
  "MetricType", STRING,
  { {"Sales"}, {"Profit"} }
)

2) Dynamic Measure

Total_Metric :=
SWITCH(
  SELECTEDVALUE('Metric Selector'[MetricType], "Sales"),
  "Sales",  SUM(FactSales[Sales]),
  "Profit", SUM(FactSales[Profit]),
  BLANK()
)
Example Use User Selection Sample Output (Card) Sample Output (Bar by Category) Notes
Card showing chosen metric Sales 650 Furniture=300, Tech=350 Measure reads slicer choice with SELECTEDVALUE.
Same visuals, different metric Profit 75 Furniture=10, Tech=65 No relationship needed between selector table and FactSales.

Level 6 — CALCULATE & Filter Patterns

CALCULATE basics

Sales_Tech :=
CALCULATE(
  [Total_Sales],
  FactSales[Category] = "Tech"
)
Pattern DAX Example Use Sample Output Notes
Override / apply filter 
Sales_Tech :=
CALCULATE([Total_Sales], FactSales[Category] = "Tech")
 Tech-only KPI 350 CALCULATE modifies filter context.
Remove filter (ALL) 
Sales_AllCats :=
CALCULATE([Total_Sales], ALL(FactSales[Category]))
 Total line on chart 650 Returns overall total even inside Category bars.
Remove all filters (REMOVEFILTERS) 
Sales_GrandTotal :=
CALCULATE([Total_Sales], REMOVEFILTERS())
 True grand total 650 Ignores all filters (use carefully).

Level 7 — Iterators (SUMX, AVERAGEX, etc.)

Use iterators when you need row-by-row logic before aggregating.

Problem DAX Example Use Sample Output Notes
Sum only positive profit 
Positive_Profit :=
SUMX(
  FactSales,
  IF(FactSales[Profit] > 0, FactSales[Profit], 0)
)
 “Profit (only gains)” KPI 85 20 + 60 + 5 = 85. Condition is per-row.
Weighted average (pattern) 
Weighted_Avg_Example :=
DIVIDE(
  SUMX(FactSales, FactSales[Sales] * FactSales[Profit]),
  SUM(FactSales[Sales])
)
 Weighted metrics (depends) Common “SUMX numerator / SUM denominator” structure.

Level 9 — Time Intelligence (Requires Date Table)

Best practice: Create a proper Date table (DimDate) and relate it to FactSales[OrderDate]. Many time functions expect a contiguous date column.

Date =
ADDCOLUMNS(
  CALENDAR(DATE(2024,1,1), DATE(2026,12,31)),
  "Year", YEAR([Date]),
  "MonthNum", MONTH([Date]),
  "MonthName", FORMAT([Date], "MMM")
)
Sales_YTD :=
TOTALYTD([Total_Sales], Date[Date])

Sales_LY :=
CALCULATE(
  [Total_Sales],
  SAMEPERIODLASTYEAR(Date[Date])
)
Function When to Use Notes
TOTALYTD Running total for the year Mark Date table as Date table in Power BI.
SAMEPERIODLASTYEAR YoY comparisons Works best with complete Date table + relationships.

Level 10 — Virtual Tables (SUMMARIZE / FILTER / ADDCOLUMNS)

Virtual tables are created inside measures. They unlock advanced patterns (custom grouping, intermediate tables, etc.).

Problem DAX When to Use Notes
Group inside a measure 
ByCategory_Table :=
SUMMARIZE(
  FactSales,
  FactSales[Category],
  "Sales", [Total_Sales],
  "Profit", [Total_Profit]
)
 Intermediate computations Returns a table (used inside other expressions).
Filter rows (table function) 
HighSalesRows :=
FILTER(FactSales, FactSales[Sales] > 100)
 Used with iterators / advanced filters FILTER returns a table; often combined with CALCULATE or X functions.

Level 11 — Debugging DAX (Practical)

Problem Technique Example Why it Helps
Measure looks “wrong” Inspect context with a table visual Add Category + Date + measure See exactly which filters produce which value.
Complex measure Use VAR for intermediate values 
Test :=
VAR s = [Total_Sales]
VAR p = [Total_Profit]
RETURN DIVIDE(p,s)
 Readable + easier to debug + sometimes faster.

Level 12 — Performance & Modeling Rules

Rule Why Action
Prefer star schema Faster filters + simpler DAX Dimensions filter facts via relationships
Prefer measures over calculated columns Less memory; dynamic results Use columns only for grouping/slicing/row logic
Avoid FORMAT() for numeric measures Converts number → text Format in Model instead
Use VAR Reduces repeated computation Store common sub-expressions
Be careful with FILTER + iterators Can be expensive Use simpler filters where possible
