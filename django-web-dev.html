1. Client vs Server

CLIENT SIDE                              SERVER SIDE
-----------                              -----------
Browser / Mobile App                     Web Server / App Server
HTML                                     Nginx / Apache / Cloud load balancer
CSS                                      Django app
JavaScript                               Python code
Cookies                                  ORM
Forms                                    Database
HTTP requests                            Files / media / static resources
HTTP responses
Note: Read this as a boundary line: browser code runs on the user's device, while Django, Python, the ORM, and the database run on the server.
Important idea: Django runs on the server. The browser does not run Django. The browser sends HTTP requests, and Django receives those requests and returns HTTP responses.

Browser
  -> HTTPS port 443
  -> Nginx / Apache / Load balancer
  -> Gunicorn / uWSGI / ASGI server
  -> Django app
  -> Database

Development vs Production: Development usually runs directly with Django's built-in development server: 
Browser
  -> Django runserver (:8000)
You start it with: 
python manage.py runserver
No Nginx, Apache, Gunicorn, uWSGI, Daphne, or Uvicorn is usually needed while learning or testing locally. Production is different: 
Browser
  -> HTTPS :443
  -> Nginx / Apache / Load balancer
  -> Gunicorn / uWSGI / Uvicorn / Daphne
  -> Django
Production servers need better performance, security, worker management, HTTPS handling, logging, and reliability.

What is a Python App Server? Django itself is a web framework, not a production web server. Gunicorn, uWSGI, Daphne, and Uvicorn are application servers that run your Django code and handle incoming requests from Nginx, Apache, or another front-facing server. Think of them as the production replacement for: 
python manage.py runserver
Common choices: 
Gunicorn = traditional Django websites and APIs
uWSGI    = older but powerful WSGI server
Uvicorn  = ASGI server for async Django
Daphne   = commonly used with Django Channels/WebSockets
They usually do not listen directly on public ports 80 or 443. Nginx normally receives public traffic first, then forwards the request internally to the Python app server.

4. HTTP Request Structure

An HTTP request has:

1. Request line
2. Headers
3. Blank line
4. Body, optional
Note: Beginner tip: read this block from top to bottom and connect it to the request flow: browser sends data, Django processes it, and a response comes back.

Example GET request:

GET /books/?page=2&search=python HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Accept: text/html
Accept-Language: en-US
Cookie: sessionid=abc123; csrftoken=token123
Note: This is a browser page request. The path tells Django what page is being requested, and headers provide extra details like cookies and browser type.

Example POST request:

POST /books/create/ HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded
Cookie: sessionid=abc123; csrftoken=token123
Content-Length: 37

title=Python+Book&price=29.99
Note: This is a form submission. The browser sends field names and values in the request body, and Django usually reads them from request.POST.

Example JSON API request:

POST /api/books/ HTTP/1.1
Host: example.com
Content-Type: application/json
Authorization: Bearer abc.jwt.token
Cookie: sessionid=abc123

{
  "title": "Python Book",
  "price": 29.99
}
Note: This is an API-style request. The client sends JSON data, and the Authorization header is commonly used to prove who the caller is.

5. HTTP Request Parts

URL

https://example.com:443/books/5/?format=json#section1
Note: A URL has several parts. Django mainly receives the path and query string; the fragment after # usually stays inside the browser.
Part Example
Scheme https
Host example.com
Port 443
Path /books/5/
Query string ?format=json
Fragment #section1

Important: fragment #section1 is handled by the browser, usually not sent to server.

Headers

Headers are metadata.

Host: example.com
User-Agent: Mozilla/5.0
Accept: text/html
Accept-Encoding: gzip
Content-Type: application/json
Authorization: Bearer token
Cookie: sessionid=abc123
Note: Headers are extra information about the request. Django can read them through request.headers when your view needs metadata.

Cookie header

Browser sends cookies to server:

Cookie: sessionid=abc123; theme=dark
Note: Cookies are automatically sent back to the server by the browser. Django uses this pattern for sessions and login state.

Django reads cookies:

request.COOKIES.get("sessionid")
Note: Cookie operations happen on the response or request. The browser stores cookies and sends them back on later requests.

Body

GET usually has no body. POST/PUT/PATCH usually has body.

Form body:

Content-Type: application/x-www-form-urlencoded

username=loc&password=secret
Note: This is the normal encoding for many HTML forms. Django converts this body into request.POST for easier access.

JSON body:

Content-Type: application/json

{
  "username": "loc",
  "password": "secret"
}
Note: JSON bodies are common for APIs. In plain Django you may parse request.body; in Django REST Framework you usually use request.data.

File upload body:

Content-Type: multipart/form-data
Note: This content type is used when a form uploads files. Django places uploaded files in request.FILES.

9. Django Request Flow

1. Browser sends HTTP request
2. Web server receives request
3. Request goes to Django
4. Django creates HttpRequest object
5. Middleware runs
6. URLconf finds matching route
7. View runs
8. View may call ORM/database
9. View may render template
10. View returns HttpResponse
11. Middleware runs again
12. Response goes back to browser
Note: This is Django's request lifecycle. For beginners, remember the core path: URL finds a view, the view does work, then returns a response.

from django.db import models


class Author(models.Model):

        return self.name


class Book(models.Model):

Step 11: Create views in books/views.py

from django.shortcuts import render, get_object_or_404, redirect
from .models import Book
from .forms import BookForm


def book_list(request):
    books = Book.objects.select_related("author").all()
    return render(request, "books/book_list.html", {"books": books})


def book_detail(request, book_id):
    book = get_object_or_404(Book, id=book_id)
    return render(request, "books/book_detail.html", {"book": book})


def book_create(request):
    if request.method == "POST":
        form = BookForm(request.POST)

        if form.is_valid():
            form.save()
            return redirect("book_list")
    else:
        form = BookForm()

    return render(request, "books/book_form.html", {"form": form})
Note: A view is a Python function that receives request and returns a response. Here, views query books, render templates, or save form data.

15. ORM Basic Concept

ORM means:

Object Relational Mapper
Note: The ORM lets you work with database data using Python classes and methods instead of writing SQL for every operation.

It converts Python objects to database rows.

Python class       -> database table
Python attribute   -> table column
Python object      -> table row
ORM query          -> SQL query
Note: The ORM lets you work with database data using Python classes and methods instead of writing SQL for every operation.

Example:

Book.objects.filter(price__gt=20)
Note: Django translates this QuerySet into SQL behind the scenes. price__gt means price greater than 20.

is similar to:

SELECT * FROM book WHERE price > 20;
Note: This SQL is shown only to explain what the ORM roughly does. In normal Django code, you usually write the ORM version.

23. ORM Performance

Problem: too many queries

Bad:

for book in books:
    print(book.author.name)
Note: all() returns a QuerySet for every row in that table. It is lazy until Django actually needs the results.

May cause one query for books, then many queries for authors.

Use select_related

For ForeignKey and OneToOneField :

ForeignKey / OneToOne      -> select_related
ManyToMany / reverse FK    -> prefetch_related

Authentication vs Authorization in SPA

Authentication:
    Who is this user?
    Example: login with username/password.

Authorization:
    What can this user do?
    Example: user can view books but cannot delete books.
Note: Authentication proves identity. Authorization checks permissions after identity is known.

JWT login flow

1. React sends username/password to Django.
2. Django validates credentials.
3. Django returns access token and refresh token.
4. React stores token depending on security design.
5. React sends access token with API requests.
6. Django validates token.
7. Django checks permissions.
8. Django returns JSON response.
Note: JWT is common in SPAs, but token storage must be designed carefully to reduce XSS and CSRF risks.
